# Мои заметки по ДЗ 4

Смысл задания не в том, чтобы просто еще раз поднять ВМ. Тут скорее проверка, что я понял, как Terraform начинает жить в реальном проекте:

- не писать один огромный `main.tf`;
- выносить повторяемые куски в модули;
- передавать значения через переменные;
- смотреть, что реально лежит в state;
- уметь вытащить ресурс из state и вернуть обратно через import.

## Что тут было по шагам

Сначала взял remote-модуль для ВМ. Это типа готовая обертка: я не пишу ресурс `yandex_compute_instance` руками, а вызываю модуль два раза. Один раз для `marketing`, второй для `analytics`.

Потом сделал `cloud-init`. Это удобно, потому что ВМ после старта сама создает пользователя, кладет SSH-ключ и ставит nginx. То есть не надо после создания руками заходить и добивать пакеты.

Дальше сделал свой модуль `vpc`. Это уже похоже на нормальную работу: если завтра надо будет еще окружение, я не копирую сеть и подсеть руками, а просто вызываю модуль с другим именем и CIDR.

Самое полезное тут, наверно, state. Terraform state - это его память. Если ресурс есть в облаке, но Terraform про него забыл, он попробует создать новый. Если ресурс в state есть, но в облаке его уже удалили руками, будет ругаться или пытаться пересоздать. Поэтому `state rm` и `import` надо понимать, хотя каждый день ими лучше не баловаться.

## Где я споткнулся

Я сначала попробовал сделать отдельную сеть `production-example` для демонстрации 4*. Yandex Cloud сказал, что лимит сетей кончился. Это нормальная практическая фигня: облако не бесконечное, особенно учебный аккаунт.

Решил проще: рабочую сеть оставил одну, `develop`, но VPC-модуль сделал универсальным. Он принимает список подсетей и создает сколько передали. Для зачета этого достаточно, потому что код реально умеет работать с `list(object)`.

Еще при `terraform import` подсетей поймал момент: когда подсети удалены из state, outputs модуля временно неполные. Из-за этого VM-модули не могли получить subnet id. Поправил outputs через `try(...)`, чтобы import можно было делать пошагово.

## Что запомнить

`terraform plan` - всегда смотреть перед apply. Он показывает, что Terraform собирается сделать.

`terraform state list` - посмотреть, чем Terraform управляет.

`terraform state rm` - убрать ресурс из памяти Terraform, но не удалить в облаке.

`terraform import` - привязать уже существующий ресурс обратно к Terraform.

`terraform-docs` - быстро делает README по модулю. Руками такое писать скучно и легко забыть обновить.

`cloud-init` - удобная штука для первичной настройки ВМ. В этом ДЗ через него ставился nginx.

## Как бы я это применял в работе

Модули полезны, когда окружения повторяются. Например:

- `dev`;
- `stage`;
- `prod`.

Один модуль сети, один модуль ВМ, разные переменные. Так меньше копипасты и меньше шансов ошибиться в одном окружении.

State лучше хранить не локально, а в удаленном backend, но это уже следующая тема. Локальный state норм для учебы, но в команде быстро начнутся проблемы.
