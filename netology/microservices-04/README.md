# Домашнее задание к занятию «Микросервисы: масштабирование»

## Задача 1. Кластеризация

Для развёртывания и эксплуатации микросервисов я бы выбрал Kubernetes. В качестве среды выполнения контейнеров — containerd, для внешней HTTP-маршрутизации — Traefik с Gateway API, для автоматического изменения числа экземпляров — Horizontal Pod Autoscaler.

Рассмотрел два варианта:

| Решение | Преимущества для задачи | Ограничения |
| --- | --- | --- |
| Kubernetes | Декларативное управление приложениями, Service и DNS, HPA, ConfigMap и Secret | Требует настройки сети, метрик, безопасности и отказоустойчивого управляющего контура |
| Docker Swarm | Простой запуск кластера, сервисы с несколькими репликами, встроенное обнаружение сервисов | Автоматическое масштабирование по метрикам нужно организовывать внешними средствами |

Swarm подошёл бы для более простой системы. Для крупной компании я бы выбрал Kubernetes: нужные механизмы управления и масштабирования можно связать через единый API, не разрабатывая собственную систему оркестрации.

### Развёртывание и запуск контейнеров

Для каждого микросервиса создаётся контейнерный образ. CI/CD собирает и проверяет его, отправляет в registry и обновляет описание приложения в Kubernetes. В production следует использовать неизменяемый тег или digest образа, а не `latest`.

Сервисы без локального состояния запускаются через Deployment. В нём задаются образ, число реплик, переменные окружения, запросы и ограничения ресурсов, проверки готовности и работоспособности. Kubernetes поддерживает заданное число экземпляров и выполняет постепенное обновление через RollingUpdate. Готовность новой реплики проверяется через readiness probe, прежде чем ей начнут направлять обычный трафик Service.

Для production я бы использовал отказоустойчивый управляющий контур и несколько рабочих узлов. Реплики одного сервиса нужно распределять между узлами, а при наличии нескольких зон — и между зонами. Само наличие нескольких pod не защищает от отказа узла, если все они запущены на нём.

### Обнаружение сервисов и маршрутизация

Для каждого внутреннего приложения создаётся Service типа ClusterIP. Его DNS-имя остаётся постоянным при пересоздании pod, поэтому другим приложениям не нужно знать адреса отдельных контейнеров. Например, сервис заказов обращается к `payments.backend.svc.cluster.local`, где `backend` — namespace.

Для внешних HTTP-запросов предлагаю следующую схему:

```text
Пользователь
    ↓ HTTPS
Облачный балансировщик
    ↓
Traefik: Gateway и HTTPRoute
    ↓
Внутренние Services → готовые реплики приложений
    ↓
Базы данных и брокер в закрытой сети
```

Traefik запускается в нескольких экземплярах за балансировщиком. В Gateway описываются точки входа и TLS, а в HTTPRoute — правила выбора backend по домену и пути. Для работы нужны установленные ресурсы Gateway API и включённый соответствующий provider Traefik: одних YAML-объектов без контроллера недостаточно.

Здесь Traefik отвечает за входящий HTTP-трафик. Если в системе уже используется Kong для проверки токенов и правил API, его можно оставить внешним шлюзом вместо дублирования одинаковых функций двумя прокси.

### Горизонтальное и автоматическое масштабирование

Вручную число экземпляров меняется через `replicas` в Deployment. Service продолжает обслуживать тот же адрес, а новые готовые pod включаются в обработку запросов.

Для автоматического масштабирования используется HPA. Например, для API можно задать от двух до десяти реплик и целевую загрузку CPU 60% относительно `requests.cpu`. Это начальные параметры, которые нужно уточнить нагрузочными тестами, а не универсальные значения.

Метрики CPU и памяти для HPA предоставляет Metrics Server. В контейнерах нужно определить requests: без них процентная загрузка соответствующего ресурса не может быть корректно рассчитана. Для масштабирования по длине очереди или частоте запросов потребуется источник пользовательских или внешних метрик и адаптер к API метрик Kubernetes. Одной установки Prometheus для этого недостаточно.

Чтобы число реплик не менялось при каждом коротком всплеске, настраиваются ограничения скорости масштабирования и окно стабилизации уменьшения. HPA управляет количеством pod, но не создаёт рабочие узлы. Если ресурсов для новых pod не хватает, отдельно нужен Cluster Autoscaler с поддержкой выбранного облака и настроенными группами узлов. Следует учитывать время выделения машин, квоты и верхний предел расходов.

Приложения не должны хранить единственную копию сессии в памяти конкретного экземпляра. Состояние выносится в общее хранилище, а повторная обработка фоновых сообщений должна быть безопасной. Масштабирование БД и брокеров планируется отдельно: увеличение числа API-pod само по себе не снимает ограничения этих компонентов.

### Разделение внешних и внутренних ресурсов

Публичный адрес получает только входной шлюз через Service типа LoadBalancer и интеграцию с облачным балансировщиком. Внутренние API остаются ClusterIP, а БД и брокер не публикуются в интернет. Рабочие узлы размещаются в закрытых подсетях; административный доступ ограничивается защищённой сетью и правилами firewall.

Одного ClusterIP или разделения по namespaces недостаточно для сетевой изоляции. Нужен CNI-плагин с поддержкой NetworkPolicy. Я бы запретил межсервисные соединения по умолчанию, затем разрешил только необходимые направления: от шлюза к API, от API к нужной БД или брокеру, обращения к DNS и другим обязательным зависимостям. Правила должны учитывать и входящий, и исходящий трафик.

Production лучше отделить от разработки отдельным кластером. Внутри кластера права команд ограничиваются через RBAC, а потребление ресурсов — через ResourceQuota и LimitRange.

### Конфигурация и чувствительные данные

Обычные настройки хранятся в ConfigMap, пароли и ключи — в Secret. Приложение получает нужные значения через `env.valueFrom.configMapKeyRef` и `env.valueFrom.secretKeyRef`. В образе остаётся код, а конфигурация задаётся для конкретного окружения.

Secret сам по себе не означает безопасное хранение: base64 — это кодирование, а не шифрование. Нужно включить шифрование секретов в etcd, ограничить доступ через RBAC и защитить резервные копии. Право создавать pod в namespace также требует ограничения, поскольку через pod можно получить доступ к доступным ему секретам.

Реальные значения не должны попадать в Git, образы и логи CI/CD. Их следует передавать из защищённого хранилища через отдельный процесс с минимальными правами, а манифесты приложений должны содержать только ссылки на Secret.

При изменении Secret значения, переданные через переменные окружения, не обновятся в уже работающем процессе. Поэтому ротация должна включать управляемое пересоздание pod и проверку приложения с новым значением.
