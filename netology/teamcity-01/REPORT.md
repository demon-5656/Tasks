# TeamCity: настройка CI

## Что делал

Под задание поднял отдельную сеть `teamcity-net` и подсеть `10.10.0.0/24` в Yandex Cloud. Не стал складывать TeamCity в уже существующую VM: так проще потом выключить или удалить весь учебный стенд без последствий для остальных сервисов.

Внутри сети созданы три машины:

| Машина | Ресурсы | Внутренний IP | Для чего |
|---|---:|---|---|
| `teamcity-server` | 4 vCPU, 4 GB RAM | `10.10.0.10` | TeamCity Server |
| `teamcity-agent` | 2 vCPU, 4 GB RAM | `10.10.0.11` | TeamCity Build Agent |
| `teamcity-runner` | 2 vCPU, 4 GB RAM | `10.10.0.12` | отдельная VM под запуск playbook |

На сервере и агенте Docker ставится через cloud-init. TeamCity Server работает в контейнере `jetbrains/teamcity-server:2023.11.4`; для данных и логов использованы Docker volumes, поэтому обновление контейнера не должно снести настройки. Агент запускается из `jetbrains/teamcity-agent:2023.11.4` и уже знает адрес сервера внутри VPC:

```text
SERVER_URL=http://10.10.0.10:8111
```

## Проверка

Сразу после создания проверил состояние VM через YC CLI:

```text
teamcity-server  RUNNING  93.77.177.157  10.10.0.10
teamcity-agent   RUNNING  93.77.182.36   10.10.0.11
teamcity-runner  RUNNING  111.88.240.135 10.10.0.12
```

Порт TeamCity доступен снаружи:

```text
TCP/8111: OK
```

На сервер удалось подключиться по SSH. Результат проверки Docker:

```text
teamcity-server  Up  ...  0.0.0.0:8111->8111/tcp
cloud-init status: done
```

Агент тоже запущен. В его логе видно регулярную попытку регистрации через внутренний адрес `http://10.10.0.10:8111`. Это ожидаемо до завершения First Start на сервере: пока TeamCity не создал свою внутреннюю конфигурацию, он отвечает агенту `TeamCity Server is starting`.

В браузере открывается стартовая страница TeamCity, версия `2023.11.4 (build 147586)`.

## Что осталось в интерфейсе TeamCity

Стенд уже готов, но саму веб-настройку и CI-часть нужно пройти в TeamCity:

1. закончить First Start и создать администратора;
2. авторизовать появившийся агент;
3. сделать fork учебного репозитория;
4. создать проект по fork и сохранить autodetect-конфигурацию;
5. добавить условные Maven-шаги: `mvn clean deploy` для `master`, `mvn clean test` для feature-веток;
6. добавить `settings.xml` с учётными данными Nexus в Maven settings TeamCity;
7. проверить deploy в Nexus, мигрировать конфигурацию в репозиторий и собрать JAR как артефакт;
8. сделать ветку `feature/add_reply`, добавить метод с `hunter`, тест, push и merge в `master`.

## Вывод

Самая неприятная часть тут не Maven, а связка из трёх машин: сервер должен быть доступен агенту по приватной сети, а наружу нужен только интерфейс TeamCity. Поэтому адрес агента задан не через постоянно меняющийся публичный IP, а через фиксированный внутренний `10.10.0.10`.
