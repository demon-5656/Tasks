# Домашнее задание к занятию 17 «Инцидент-менеджмент»

## Постмортем: сбой GitHub 21–22 октября 2018 года

Разбор составлен по опубликованному постмортему GitHub и русскоязычной заметке на Habr. Технические причины и хронологию взял из первоисточника; Habr использовал для описания того, как сбой выглядел со стороны пользователя. Собственные предложения по улучшению выделены отдельно.

### 1. Краткое описание

| Параметр | Значение |
| --- | --- |
| Начало | 21 октября 2018 года, 22:52 UTC.[1] |
| Окончание деградации | 22 октября 2018 года, 23:03 UTC — статус переведён в green.[1] |
| Продолжительность | 24 часа 11 минут.[1] |
| Тип инцидента | Разрыв сетевой связности, автоматическое переключение MySQL между регионами и нарушение согласованности метаданных.[1] |
| Основные затронутые функции | Работа с метаданными сайта, доставка webhooks, сборка и публикация GitHub Pages.[1] |
| Состояние после восстановления | Обработка очередей завершена, работа сервисов проверена; сверка отдельных записей продолжалась и после восстановления доступности.[1] |

При плановой замене неисправного оптического оборудования 100G пропала связь между сетевым узлом и основным дата-центром GitHub на восточном побережье США.[1] Связь восстановили через 43 секунды, но за это время система автоматического failover начала переносить роль primary баз данных на западное побережье.[1]

Кратковременная сетевая проблема превратилась в длительный инцидент: базы в разных регионах получили расходящиеся записи, а приложения не были рассчитаны на работу с удалёнными primary через межрегиональный канал.[1] GitHub выбрал сохранение целостности данных, даже ценой более долгого восстановления сервиса.[1]

### 2. Влияние на пользователей и данные

- Пользователи видели устаревшие и несогласованные данные сайта. На Habr описан конкретный симптом: созданная issue или комментарий появлялись, а после обновления страницы визуально пропадали.[1][2]
- Значительную часть инцидента не доставлялись webhooks и не выполнялись сборка и публикация GitHub Pages.[1]
- Git-данные репозиториев оставались неизменными и доступными: сбой затронул прежде всего метаданные в MySQL, а не само хранилище Git-объектов.[2]
- К моменту разбора очередей накопилось более **5 млн webhook-событий** и **80 тыс. сборок Pages**.[1]
- При возобновлении обработки около **200 тыс. webhook payloads** были отброшены из-за истёкшего внутреннего TTL. Обнаружив это, инженеры приостановили обработку и временно увеличили TTL.[1]

Фразу «данные не потеряны» здесь нельзя понимать как «вообще никаких потерь и незавершённых работ». GitHub заявил об отсутствии потери пользовательских данных, но в опубликованном разборе ещё продолжалась сверка записей, оставшихся только в исходном дата-центре.[1] Например, в одном из наиболее загруженных кластеров таких записей было 954 — это не общее количество по всем кластерам.[1] Отброшенные webhook payloads описаны отдельно, и увеличение TTL само по себе не доказывает их повторную доставку.[1]

Точное число затронутых пользователей, финансовый ущерб и величина нарушения SLA в приведённых источниках не указаны. Поэтому числовые оценки этих показателей в разбор не добавлял.

### 4. Причины инцидента

#### Пусковое событие

Потеря сетевой связности во время замены оборудования. Сама по себе она длилась меньше минуты.[1]

#### Основная системная причина

Политика автоматического переключения БД не соответствовала ограничениям приложений. Orchestrator разрешал назначение primary в другом регионе и действовал согласно своей конфигурации.[1] Приложения на восточном побережье не выдерживали дополнительную задержку большого числа обращений к MySQL на западном побережье.[1]

То есть проблема не сводится к тому, что «Orchestrator сломался» или кто-то неправильно заменил оборудование. Защита от отказа БД допустила топологию, которая была непригодна для нормальной работы приложения.

#### Почему нельзя было просто переключить всё обратно

В восточном дата-центре остались записи за короткий интервал, которые ещё не успели реплицироваться на запад.[1] После переключения западные primary начали принимать новые записи.[1] В результате обе стороны содержали данные, отсутствовавшие на другой стороне; безопасный немедленный возврат к прежним primary был невозможен.[1]

Кворум Orchestrator решил вопрос управления топологией, но не устранил расхождение уже записанных данных между MySQL-кластерами.[1] Поэтому восстановление потребовало не только переключения ролей, но и работы с копиями данных и репликацией.[1]

#### Что увеличило время восстановления

- Пришлось восстанавливать многотерабайтные базы из удалённого облачного хранилища. Время уходило на передачу, распаковку, проверку контрольных сумм, подготовку и загрузку резервных копий.[1]
- Реплики догоняли primary под продолжающейся нагрузкой. С началом рабочего дня в Европе и США поток записей вырос, а первоначальная линейная оценка времени синхронизации оказалась неверной.[1]
- Возврат primary на восточное побережье не устранил отставание read replicas. Чтение с разных реплик продолжало давать пользователям неодинаковые результаты.[1]
- После восстановления БД оставалась большая очередь фоновой работы. Её нельзя было обработать без ограничений, не рискуя перегрузить GitHub и получателей уведомлений.[1]

### 5. Восстановление и принятые решения

Основной приоритет команды — целостность данных.[1]
Для этого ограничили изменения инфраструктуры, приостановили отдельные фоновые процессы, восстановили базы и синхронизировали реплики.[1]
Для уменьшения отставания добавили мощности для чтения.[1]
Только после стабилизации БД начали разбирать очереди.[1]

Резервные копии создавались каждые четыре часа, а процедура восстановления проверялась как минимум ежедневно.[1] Поэтому проблема была не в отсутствии бэкапов: раньше команде не приходилось полностью восстанавливать целый кластер таким способом, и масштаб текущей аварии оказался тяжелее прежних сценариев восстановления.[1]

Переход в green отложили до обработки оставшихся очередей и проверки нормальной работы.[1] При этом возврат доступности не означал завершения всей последующей сверки расходящихся записей из MySQL binlog.[1]

### 6. Что сработало и что стоит улучшить

**Сработало:**

- Мониторинг обнаружил проблему через две минуты, затем были подключены координатор инцидента и специалисты по БД.[1]
- Команда явно выбрала сохранение данных, а не рискованный быстрый откат.[1]
- Были резервные копии, проверенная процедура восстановления и сохранённые binlog для последующей сверки записей.[1]
- Статус не вернули в green сразу после ускорения сайта — дождались завершения оставшейся обработки и проверок.[1]

**Не сработало:**

- Автоматический failover создал топологию, которую приложения не поддерживали по задержкам.[1]
- Прогноз восстановления не учёл рост нагрузки и нелинейную скорость догоняющей репликации.[1]
- Публичные статусы green/yellow/red не позволяли достаточно точно показать, какие компоненты работают, а какие недоступны.[1]
- Канал подробной коммуникации зависел от GitHub Pages, который сам был остановлен.[1]
- TTL части webhook-сообщений оказался меньше фактического времени ожидания в очереди.[1]

### 7. Действия после инцидента

#### Меры, объявленные GitHub

Это планы из постмортема, опубликованного 30 октября 2018 года, а не утверждение об их выполнении к настоящему времени.[1]

| Мера | Какую проблему решает |
| --- | --- |
| Ограничить Orchestrator: не допускать автоматического назначения primary за границами региона.[1] | Не создавать топологию с неприемлемыми для приложений задержками. |
| Продолжить сверку записей по сохранённым binlog; определить, что можно восстановить автоматически, а где нужно обратиться к пользователям.[1] | Устранить оставшиеся расхождения данных. |
| Ускорить переход к покомпонентной странице статуса.[1] | Сообщать о состоянии конкретных функций, а не только о едином цвете статуса. |
| Ускорить уже начатую инициативу active/active/active с резервированием N+1 на уровне дата-центров.[1] | Подготовиться к потере целой площадки без влияния на пользователей. |
| Систематически проверять отказные сценарии, развивать fault injection и chaos engineering.[1] | Проверять архитектурные предположения до реальной аварии. |

#### Мои предложения для плана улучшений

В открытом разборе нет полного внутреннего списка исполнителей и сроков. Поэтому ниже — **предлагаемые роли и критерии приёмки**, а не реальные назначения сотрудников GitHub.

| Приоритет | Предложение | Предлагаемый ответственный | Критерий проверки |
| --- | --- | --- | --- |
| P0 | Проверить политику failover в тестовом сценарии изоляции региона. | Команда БД и SRE | Ни одна автоматическая операция не переносит primary в неподдерживаемую приложением топологию. |
| P0 | Подготовить runbook для расходящихся записей после переключения primary. | Команда БД | На тестовом наборе подтверждены сохранение обеих ветвей записей, сверка и контролируемое восстановление. |
| P1 | Провести учение с полным восстановлением крупного кластера под нагрузкой. | Команда БД, SRE и владельцы приложений | Измерены загрузка бэкапа, восстановление, догоняющая репликация и обработка очередей; результат сопоставлен с согласованными RTO/RPO. |
| P1 | Добавить алерты на lag реплик, возраст старейшего сообщения и долю отброшенных сообщений. | Команды мониторинга и фоновой обработки | В тесте оператор получает сигнал до нарушения согласованного порога; истечение TTL не остаётся незамеченным. |
| P1 | Проверить восстановление очередей с ограничением скорости и контролем повторной доставки. | Владельцы webhooks и Pages | Очередь разбирается без перегрузки зависимых систем; явно определено, как обрабатываются просроченные сообщения и дубликаты. |
| P1 | Обеспечить независимый канал сообщений об аварии и шаблон регулярных обновлений. | Координатор инцидентов и команда коммуникаций | Сообщение публикуется при недоступном основном сервисе; факты отделены от предварительного ETA. |

Сроки этих работ должны быть согласованы с ответственными после оценки объёма. Придумывать даты закрытия и выдавать их за фактический план GitHub было бы неправильно.
