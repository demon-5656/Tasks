# Домашнее задание к занятию «Микросервисы: подходы»

В работе подобрал инструменты для разработки, централизованного сбора логов и мониторинга микросервисной системы. При выборе учитывал требования задания и сложность эксплуатации.

## Задача 1. Обеспечение разработки

Рассмотрел три облачные платформы со встроенным CI/CD.

| Платформа | Ручной запуск с параметрами | Собственные агенты и образы | Параллельное выполнение |
| --- | --- | --- | --- |
| GitLab.com | Pipeline inputs и CI/CD variables | Self-hosted GitLab Runner, Docker executor | Параллельные jobs и `parallel:matrix` |
| GitHub | Параметры `workflow_dispatch` | Self-hosted runners, jobs в контейнерах | Независимые jobs и matrix strategy |
| Bitbucket Cloud | Custom pipelines и переменные | Self-hosted runners, собственные Docker-образы | Параллельные steps |

### Выбор

Я бы выбрал GitLab.com, GitLab CI/CD и собственные раннеры GitLab. Платформа объединяет хранение кода и управление сборками, а раннеры можно разместить внутри инфраструктуры компании.

Для каждого микросервиса создаётся отдельный Git-репозиторий. Вместе с кодом в нём хранятся `Dockerfile`, тесты и `.gitlab-ci.yml`. Типовой pipeline состоит из нескольких этапов:

```text
lint → test → build → publish → deploy
```

Сборка автоматически запускается при `push`, создании merge request или создании тега. Для нестандартного запуска используется кнопка New pipeline. Перед запуском можно указать типизированные inputs или переменные, например окружение, версию образа и необходимость интеграционных тестов.

Один файл `.gitlab-ci.yml` может содержать несколько конфигураций сборки. Через `rules` выбираются jobs для нужной ветки, тега, события или параметра. Общие шаги выносятся в шаблоны и подключаются через `include`, а конкретные jobs расширяют их через `extends`. Это уменьшает копирование одинаковой конфигурации между сервисами.

Внутри job можно запускать любые команды и проектные скрипты: статический анализ, тесты, миграции, сборку пакета или публикацию контейнерного образа. Через `image` задаётся готовый или собственный Docker-образ со всеми нужными SDK и утилитами.

Пароли, токены и ключи не должны попадать в репозиторий. Их следует хранить в CI/CD variables или во внешнем хранилище секретов. Переменные для production нужно ограничить защищёнными ветками, замаскировать в логах и передавать только тем заданиям, которым они нужны.

Раннеры GitLab устанавливаются на собственных серверах и разделяются тегами, например `docker`, `test` и `deploy`. Отдельный защищённый раннер можно оставить только для развёртывания. Обычные сборки не должны получать доступ к production.

Несколько pipeline из разных репозиториев могут выполняться одновременно, если развёрнуто достаточно раннеров и в их конфигурации разрешена нужная конкурентность через `concurrent` и `limit`. Внутри одного pipeline независимые задания выполняются параллельно при наличии свободных раннеров, а большой набор тестов можно разделить через `parallel` или `parallel:matrix`. Публикация образа и развёртывание начинаются только после успешного завершения обязательных проверок.

GitHub Actions тоже закрывает требования задания. GitLab я выбрал из-за единой конфигурации репозитория и CI/CD, развитых шаблонов и удобного управления собственными раннерами. Bitbucket Pipelines подходит для более простой схемы, но в данном случае не даёт заметного преимущества.

## Задача 2. Централизованный сбор логов

Для логов рассмотрел следующие варианты.

| Решение | Доставка | Поиск | Интерфейс |
| --- | --- | --- | --- |
| Vector, Elasticsearch и Kibana | Checkpoint, дисковый буфер и подтверждения | Полнотекстовый поиск, фильтры и агрегации | Kibana |
| Filebeat, Elasticsearch и Kibana | Дисковая очередь и повторные попытки | Те же возможности Elasticsearch | Kibana |
| Grafana Alloy, Loki и Grafana | Очередь и повторные попытки на стороне Alloy | Поиск по меткам и LogQL | Grafana |

### Выбор

Я бы использовал Vector, Elasticsearch и Kibana.

```text
stdout и stderr приложений
            ↓
локальные журналы контейнеров
            ↓
Vector на каждом узле
            ↓
Elasticsearch
            ↓
Kibana
```

Приложения продолжают писать в `stdout` и `stderr`, поэтому серьёзных изменений в коде не потребуется. Контейнерная среда сохраняет этот вывод в локальные файлы. Vector читает их, разбирает записи, добавляет метаданные и отправляет события в Elasticsearch. В Kubernetes Vector можно запускать как DaemonSet, а на обычных серверах — как системную службу.

К каждой записи добавляются время события, окружение, имя сервиса, хост, контейнер или pod и уровень сообщения. Если приложение пишет JSON, его поля разбираются отдельно. Обычная строка сохраняется в поле `message`.

Vector запоминает позицию чтения файла. Для очереди между агентом и Elasticsearch используется дисковый буфер с режимом `when_full = "block"`, а запись удаляется из него после подтверждения приёма. Если Elasticsearch временно недоступен, Vector повторяет отправку после восстановления связи.

Такая схема даёт доставку по модели `at-least-once`: потеря связи или перезапуск агента не должны приводить к пропуску уже записанных событий, но возможны дубли. Абсолютной гарантии при выходе диска узла из строя или одновременной потере исходного файла и буфера нет. Поэтому нужно следить за размером очереди, свободным местом, ошибками отправки и сроком хранения локальных журналов.

Elasticsearch хранит и индексирует записи. Для него нужно заранее настроить шаблоны полей, ротацию индексов и срок хранения, иначе объём данных будет расти без ограничения. Реплики защищают от отказа отдельного узла, но не заменяют резервные копии.

Разработчики работают с логами через Kibana Discover. Там можно искать по тексту, времени, сервису, окружению и уровню ошибки. Сохранённая сессия хранит запрос, фильтры, выбранные столбцы и сортировку. На неё можно выдать постоянную ссылку пользователям с правом чтения нужных индексов.

В центральное хранилище нельзя отправлять пароли, токены и персональные данные без необходимости. Чувствительные поля нужно удалять или маскировать в Vector до отправки в Elasticsearch.

Loki потребляет меньше ресурсов и хорошо подходит для поиска по меткам, но Elasticsearch удобнее для произвольного полнотекстового поиска и фильтрации по большому числу структурированных полей. Filebeat также подходит, однако Vector можно использовать и для преобразования, и для маршрутизации событий в одном агенте.

## Задача 3. Мониторинг

Рассмотрел три варианта мониторинга.

| Решение | Системные метрики | Метрики контейнеров и приложений | Интерфейс |
| --- | --- | --- | --- |
| Prometheus и Grafana | Через exporters | cAdvisor и `/metrics` приложений | PromQL и Grafana |
| Zabbix | Агенты и готовые шаблоны | Требуются дополнительные шаблоны и интеграции | Встроенный интерфейс |
| Telegraf, InfluxDB и Grafana | Через Telegraf | Плагины и прикладные метрики | InfluxQL или Flux и Grafana |

### Выбор

Для этой системы я бы использовал Prometheus и Grafana со следующими источниками метрик:

- `node_exporter` для Linux-хостов;
- `cAdvisor` для контейнеров;
- эндпоинт `/metrics` в каждом приложении;
- отдельные exporters для СУБД, брокеров и других готовых компонентов.

```text
node_exporter ──────────┐
cAdvisor ───────────────┼──> Prometheus ──> Grafana
метрики приложений ─────┘
```

Prometheus периодически опрашивает все зарегистрированные эндпоинты и сохраняет временные ряды. Метка `instance` разделяет экземпляры, а дополнительные метки позволяют выбирать сервис, окружение и кластер.

`node_exporter` собирает с каждого хоста загрузку CPU, использование RAM, состояние файловых систем и дисков, сетевой трафик и ошибки интерфейсов. Для Windows-хостов вместо него понадобится `windows_exporter`.

`cAdvisor` показывает для каждого контейнера потребление CPU и памяти, сетевой трафик, объём занятого места в файловой системе и дисковые операции. Эти показатели можно группировать по сервису и экземпляру. Для постоянных томов при необходимости дополнительно собираются метрики используемой системы хранения. Если процесс работает вне контейнера, его метрики придётся собирать отдельным экспортёром или средствами операционной системы.

Системные экспортёры не видят внутреннее состояние сервиса. Поэтому приложение должно публиковать собственные метрики: количество запросов, ошибки, длительность обработки, активные соединения, размер очереди и другие показатели, связанные с его назначением.

Для запросов и агрегации используется PromQL. С его помощью можно получить состояние отдельного экземпляра или сумму и скорость изменения показателей по всему сервису. В метки нельзя записывать request ID, user ID и другие уникальные значения: высокая кардинальность быстро увеличит нагрузку на Prometheus.

Grafana подключается к Prometheus как к источнику данных. Я бы создал отдельные панели для:

1. доступности хостов и сервисов;
2. CPU, RAM, дисков и сети хостов;
3. ресурсов контейнеров;
4. частоты запросов, ошибок и задержек приложений;
5. состояния СУБД, очередей и других зависимостей.

Переменные Grafana позволяют одним набором панелей переключаться между окружениями, хостами и сервисами.

Prometheus хорошо подходит для динамической контейнерной инфраструктуры и единообразно собирает системные и прикладные метрики. Zabbix удобен для традиционных серверов и готовых проверок, но потребует больше адаптации под контейнеры. Вариант с InfluxDB тоже рабочий, однако добавляет отдельную агентскую и серверную конфигурацию без преимущества для требований этого задания.
