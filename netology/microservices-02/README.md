# Домашнее задание к занятию «Микросервисы: принципы»

В работе подобрал API Gateway и брокер сообщений для микросервисной системы. Сравнивал не только наличие нужных функций, но и сложность дальнейшей эксплуатации.

## Задача 1. API Gateway

Для сравнения взял Kong Gateway, Traefik, NGINX и KrakenD.

| Решение | Маршрутизация | Проверка аутентификации | HTTPS | Эксплуатация |
| --- | --- | --- | --- | --- |
| Kong Gateway | Services и Routes, есть декларативная конфигурация | JWT, Key Authentication и другие плагины | TLS-сертификаты и SNI | Средняя сложность, много готовых плагинов |
| Traefik | Динамические routers и services через конфигурацию и providers | Обычно через ForwardAuth и отдельный сервис авторизации | TLS и автоматическое получение сертификатов через ACME | Удобен в Docker и Kubernetes, сравнительно простой запуск |
| NGINX | Гибкая настройка через `location` и `proxy_pass` | Через `auth_request` и внешний сервис | Зрелая поддержка TLS и SNI | Надёжный и быстрый, но функции API Gateway приходится собирать вручную |
| KrakenD | Маршруты и upstream-сервисы задаются в конфигурации | Встроенная проверка JWT | Поддерживает TLS-терминацию | Удобен для агрегации API, но экосистема расширений меньше, чем у Kong |

### Выбор

Я бы выбрал Kong Gateway. Он закрывает все требования задания без написания собственного шлюза: маршруты хранятся в конфигурации, JWT можно проверить до передачи запроса в сервис, а HTTPS завершается на самом gateway.

Для крупной системы важен и запас на дальнейшее развитие. В Kong можно подключить ограничение частоты запросов, логирование и экспорт метрик. При этом сам gateway не решает вопросы мониторинга автоматически: метрики и логи всё равно нужно отправлять в отдельные системы.

Единственный экземпляр Kong станет общей точкой отказа. Поэтому в рабочем окружении нужно запускать несколько экземпляров за балансировщиком, проверять их состояние и не публиковать управляющий API наружу.

Traefik я бы выбрал для более простой динамической инфраструктуры, но полноценную проверку токена часто пришлось бы передавать отдельному сервису. NGINX даёт максимальный контроль, однако потребует больше ручной настройки. KrakenD хорошо подходит для сборки и агрегации API, но Kong удобнее как единая расширяемая точка входа для большого количества сервисов.

## Задача 2. Брокер сообщений

Сравнил RabbitMQ, Apache Kafka, NATS JetStream и ActiveMQ Artemis.

| Решение | Кластеризация | Хранение на диске | Скорость | Форматы | Разграничение доступа | Эксплуатация |
| --- | --- | --- | --- | --- | --- | --- |
| RabbitMQ | Кластер и quorum queues с репликацией | Quorum queues сохраняют сообщения на диске | Высокая, но репликация увеличивает задержку | Передаёт бинарные данные, формат выбирает приложение | Права на virtual hosts, exchanges и queues | Средняя, есть понятный интерфейс управления |
| Apache Kafka | Репликация партиций между узлами | Распределённый журнал хранится на диске | Очень высокая пропускная способность | Произвольная полезная нагрузка | ACL для топиков, групп и других ресурсов | Выше средней: нужно управлять партициями, репликацией и сроком хранения |
| NATS JetStream | Кластеризация и репликация streams | Поддерживает файловое хранилище | Очень высокая, небольшая задержка | Сообщение является набором байтов | Права на публикацию и подписку по subjects | Средняя |
| ActiveMQ Artemis | Кластер, репликация и shared-store HA | Журнал или JDBC-хранилище | Высокая | Передаёт бинарные данные, формат выбирает приложение | Роли и права для адресов и очередей | Средняя, поддерживает AMQP, MQTT, STOMP, OpenWire и Core |

Брокер обычно не разбирает бизнес-формат сообщения, а передаёт набор байтов. Поэтому JSON, Protobuf или Avro выбираются на уровне приложений. Для совместимости между сервисами отдельно потребуется договориться о схеме и её версиях.

### Выбор

Для указанных требований я бы выбрал RabbitMQ с quorum queues. Kafka быстрее на очень больших потоках и лучше подходит для долгого хранения событий с повторным чтением, но в задании также требуется простота эксплуатации. RabbitMQ проще использовать как обычную очередь для заказов, уведомлений и фоновых задач.

Quorum queues реплицируют сообщения между узлами и сохраняют их на диске. Для нормальной отказоустойчивости я бы начал с кластера из трёх узлов. Доступ можно разделить через virtual hosts и права на конкретные exchanges и queues.

Одной durable-очереди недостаточно для гарантированной обработки. Издатель должен использовать publisher confirms, а получатель отправлять acknowledgement только после успешной обработки. RabbitMQ работает по модели at least once, поэтому повторная доставка считается нормальной и обработчики должны быть идемпотентными. Для сообщений, которые постоянно завершаются ошибкой, понадобится ограничение повторов и отдельная dead letter queue.

NATS JetStream выглядит проще и быстрее, но RabbitMQ привычнее для классической модели очередей и имеет зрелые средства маршрутизации. ActiveMQ Artemis тоже закрывает требования, особенно если нужны разные протоколы, но для этого проекта не даёт явного преимущества перед RabbitMQ.

## Итог

Kong Gateway будет единой внешней точкой входа, где выполняются маршрутизация, проверка токенов и завершение HTTPS. RabbitMQ возьмёт на себя асинхронный обмен и позволит сервисам не ждать друг друга при выполнении фоновых операций.

Оба компонента нужно разворачивать отказоустойчиво. Для Kong это несколько экземпляров за балансировщиком, для RabbitMQ — кластер и quorum queues. Такой вариант закрывает обязательные требования и не добавляет лишнюю сложность без конкретной необходимости.
