# Домашнее задание «Компоненты Kubernetes»

## Ресурсы приложений

Для расчёта принимаю указанные в условии ГБ и МБ за `GiB` и `MiB`: 1 GiB = 1024 MiB. Это небольшое округление вверх относительно десятичных единиц. Число CPU считаю в ядрах/vCPU, где `0,2 CPU = 200m`.

| Компонент | Копий | CPU на копию | ОЗУ на копию | CPU всего | ОЗУ всего |
| --- | ---: | ---: | ---: | ---: | ---: |
| База данных | 3 | 1 | 4 GiB | 3 | 12 GiB |
| Кеш | 3 | 1 | 4 GiB | 3 | 12 GiB |
| Фронтенд | 5 | 0,2 | 50 MiB | 1 | 250 MiB |
| Бекенд | 10 | 1 | 600 MiB | 10 | 6000 MiB |
| **Всего** | **21** | | | **17** | **30 826 MiB ≈ 30,104 GiB** |

Проверка суммы памяти: `24 × 1024 + 250 + 6000 = 30 826 MiB`.

Эти значения беру как исходные `requests` приложения. Это расчёт под заданную нагрузку, а не замеры пикового потребления. Потребность при росте трафика придётся уточнять нагрузочным тестом.

Для разных окружений использовал бы один Helm-чарт: frontend и backend в отдельных Deployment, БД и кеш — в отдельных StatefulSet либо под управлением подходящих операторов. Количество реплик, образы, requests и настройки PVC вынес бы в values. Сам чарт дополнительных нод не требует.

## Рабочие ноды и служебный запас

Выбрал worker-ноды по **8 vCPU и 16 GiB ОЗУ**. Полностью отдавать эти ресурсы приложению нельзя: на ноде остаются ОС, kubelet, container runtime и служебные Pod. В документации Kubernetes эти расходы отдельно учитываются через резервы и Node Allocatable [1].

На каждом worker закладываю следующий бюджет:

| Назначение | CPU | ОЗУ |
| --- | ---: | ---: |
| ОС, kubelet и container runtime | 0,75 | 1 GiB |
| Служебные Pod: CNI, kube-proxy, доля DNS и ingress | 0,25 | 0,5 GiB |
| Буфер памяти до eviction | — | 0,5 GiB |
| **Всего не отдаю приложению** | **1** | **2 GiB** |

Это моя стартовая оценка для небольшого кластера, а не фиксированное требование Kubernetes. Отдельный тяжёлый стек мониторинга и централизованных логов в неё не включаю. Расходы служебных Pod не подменяю `kubeReserved`: их requests тоже нужно учитывать при размещении [1].

Для приложения на одной ноде остаётся **7 CPU и 14 GiB**. По CPU нужно `ceil(17 / 7) = 3` ноды. По памяти — `ceil(30,104 / 14) = 3`. Без учёта отказа три worker справляются.

## Запас на отказ одной ноды

Добавляю четвёртую worker-ноду. Считаю не только сохранение части приложения, но и возможность восстановить все заданные реплики после отказа.

| Состояние | Worker-нод | Доступно приложению CPU | Доступно приложению ОЗУ |
| --- | ---: | ---: | ---: |
| Все ноды работают | 4 | 28 | 56 GiB |
| Одна нода недоступна | 3 | 21 | 42 GiB |
| Требуется приложению | | 17 | 30,104 GiB |

После отказа остаётся примерно **4 CPU и 11,896 GiB** сверх расчётной нагрузки. Если оставить только три worker, после потери одной получится 14 CPU и 28 GiB: этого уже недостаточно.

Проверил также размещение отдельных реплик, чтобы не ограничиваться общей суммой. Один из вариантов на трёх оставшихся нодах:

| Нода | БД | Кеш | Фронтенд | Бекенд | CPU | ОЗУ |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| worker A | 1 | 1 | 2 | 4 | 6,4 | 10,441 GiB |
| worker B | 1 | 1 | 2 | 3 | 5,4 | 9,855 GiB |
| worker C | 1 | 1 | 1 | 3 | 5,2 | 9,807 GiB |
| **Всего** | **3** | **3** | **5** | **10** | **17** | **30,104 GiB** |

На каждой ноде укладываюсь в бюджет 7 CPU / 14 GiB. Реплики одной БД и одного кеша нужно разнести по разным нодам через pod anti-affinity. Для frontend и backend предусмотрел бы topology spread constraints, чтобы не собирать все копии на одном worker.

Три копии сами по себе не обеспечивают отказоустойчивость БД или кеша: нужны настроенная репликация, выбор лидера и переключение клиентов. Для восстановления stateful-реплик также требуется доступное хранилище. Обычный local PV на отказавшей ноде нельзя просто подключить на другой: необходимы отказоустойчивые тома либо восстановление реплики средствами самой БД/кеша. Запас CPU и памяти не делает переключение мгновенным.

## Control plane

Для управления кластером закладываю **три отдельные control-plane-ноды по 2 vCPU и 4 GiB ОЗУ**. Использую схему stacked etcd: etcd находится на этих же нодах, отдельных серверов под него в расчёте нет. Три control-plane-ноды соответствуют варианту HA-топологии из документации kubeadm [2].

Ресурсы каждой control-plane-ноды распределяю так:

| Назначение | CPU | ОЗУ |
| --- | ---: | ---: |
| ОС, kubelet, container runtime | 0,5 | 1 GiB |
| API server, scheduler, controller manager, etcd и служебный запас | 1,5 | 3 GiB |
| **Всего** | **2** | **4 GiB** |

Это стартовая оценка для небольшого проекта. Приложения на control plane не размещаю. Для API нужен отказоустойчивый endpoint: в этой схеме предполагаю VIP на control-plane-нодах, а не единственную отдельную VM-балансировщик. При потере одного участника трёхчленного etcd остаются два участника и сохраняется большинство.

Ноды нужно разместить на разных физических хостах или в независимых доменах отказа. Семь VM на одном физическом сервере не защитят от отказа самого сервера.

## Итоговая конфигурация

| Тип нод | Количество | CPU на ноду | ОЗУ на ноду | CPU всего | ОЗУ всего |
| --- | ---: | ---: | ---: | ---: | ---: |
| Control plane + etcd | 3 | 2 vCPU | 4 GiB | 6 vCPU | 12 GiB |
| Worker | 4 | 8 vCPU | 16 GiB | 32 vCPU | 64 GiB |
| **Всего** | **7** | | | **38 vCPU** | **76 GiB** |

Таким образом, беру **3 control-plane-ноды и 4 worker-ноды**. Служебные расходы уже входят в приведённые параметры. При потере одного worker оставшихся ресурсов хватает для всех 21 реплики.

Под ОС, образы, логи и etcd нужны SSD. Объём данных БД, скорость их роста, IOPS и размер резервных копий в условии не заданы, поэтому ёмкость PVC и дисков здесь не придумываю. Их нужно рассчитать отдельно; общие CPU и ОЗУ не являются полной оценкой стоимости инфраструктуры.
